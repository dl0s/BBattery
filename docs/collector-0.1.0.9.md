# 采集器 0.1.0.9 修复与恢复

验收日期：2026-10-03 UTC；北京时间为 2026-10-04。应用版本为 **0.1.0.9**，与受保护的 unsigned 安装服务 **1.0.9** 区分。

## 问题与变更

现场采集器已退出，数据库仍有旧心跳。随后应用包已升级，但后台仍使用旧启动配置；未确认操作令按钮停留在“正在确认”。此次启用包内采集器并更换 BBattery 的启动段，采集器真实返回原请求的确认结果后恢复按钮。

- 就绪同时核对持久进程锁、实例 PID/随机编号、身份、初始化后的数据库心跳和错误状态。锁空闲时旧心跳不能宣告就绪；负时差和陈旧心跳被拒绝。
- 启动最多尝试 3 次，每次观察最长 10 秒；持锁而身份不明时拒绝启动替代者。启动脚本退出后没有常驻 shell 监护器。采集器忽略 SIGHUP/SIGPIPE，业务独立于 GUI 和 SSH。
- GUI 保存原操作编号及参数摘要，重启继续核对，未确认超时保持待确认。已受理开始操作通过测试主键去重。测试开始、首次样本与成功确认，以及结束、终点样本与成功确认分别原子提交。
- 无数据结构迁移，旧版仍可读取数据库。历史达到 60 MiB 或可用空间低于 16 MiB 时拒绝新测试，SQLite 增长预算为 64 MiB；超限不删除旧记录。已有超过预算的数据库保留原大小并拒绝新测试。

## 部署与受保护能力

部署入口为 `python -B tools/device.py install`；`provision`、`boot-hook` 共用原发布意图。高权限执行使用冻结 `with_device_lock.ps1`，GUI、SSH 和 scp 观察使用 Q10Manager 同一资源键、Windows FileShare.None 锁和队列屏障。锁文件不删除。

BAR 使用已有固定主机身份的 scp 连接传输，回读核验 SHA-256 后使用；短脚本经冻结协调入口执行。两次大 heredoc 传输超时的原记录保留，改用文件传输后没有重发未知安装事务。此次发现用户已经安装相同摘要的 0.1.0.9，核对全部安装资源后完成激活，没有额外提交一次安装。

停止服务前核验新旧包，备份原 BAR、`start.sh`、btool、`history.sqlite`、`settings.ini`。数据库使用 DELETE 日志和临时写锁取得一致副本，完整性及回读检查通过后才继续。更新阶段记录保存于独立标签；启动来源出现未知字节、权限变化、未知进程或未完成安装事务时拒绝破坏性操作。QNX 的 `/proc` 文件所有者不代表有效 UID，信号前使用有界 `pidin users` 观察和当前参数核对。

启动链仅替换 btool 的 BBattery 段：旧段启动无限 shell 循环并追加日志；新段为已审阅的固定启动文件注册 PathTrust，执行有界启动并丢弃常规输出。btool 其余字节及 UID/GID/mode 保留，替换后的固定文件重新注册原信任。应用运行 UID 100、GID 902、附加组 1000。root 初始化、SSH 配置/凭据、unsigned 原生能力及其 UID 88 构造行为保持原有设置；没有对系统祖先目录递归 chmod/chown，也没有宣称修复既有祖先可写边界。

单包上限 8 MiB，数据库备份读取上限 64 MiB；维护脚本目录最多 64 个条目，创建前总量上限 64 MiB，单次脚本另受包大小限制。更新备份最多 8 组，超过时拒绝新更新并保留恢复记录；不自动清理关键证据。常规运行输出不增长服务日志。
